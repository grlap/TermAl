# Coder test execution

For a new mechanism or a significant behavior change, the item states the goal, the observed problem, the proposed behavior and its cost before code.

1. Discover the project's own instructions, build commands, launcher and any changed-path/test mapping it has. Use those existing contracts and real commands; do not create another launcher, gate or selection guarantee.
2. Own the complete working package: code, necessary test changes, build and meaningful changed-behavior checks. Select changed and new tests using what step 1 found. When uncertain, choose a wider targeted suite justified by the touched seams, not an unconditional whole-suite run. Run the project's formatter before freezing a candidate. A test proves behaviour by running the code. Don't assert on the text or shape of the code (source scans, line or size caps, counts, layout); if something needs protecting, check its effect at run time. Running a source-processing tool on fixtures is behaviour, and `source_id` only binds a result to its input; neither is such a test.
3. Run focused checks in the owned worktree with the correct cwd and environment. Do not edit the tested input while it runs and never cancel a running test to end a turn. Where a tool offers it, prefer the option that reports every failure in one run, so one run shows them all. To run them on a remote runner, hand it the exact commit: where the project's instructions let you push your candidate as a test ref, push it and give the runner the ref and commit id, and delete the ref once the evidence is recorded; otherwise use the transfer the instructions name. Send the job through the host's existing remote mailbox to the runner's registered native session on that host; never open a side SSH/SCP remote shell or file copy. The runner returns its terminal result and artifact locators through the same supported route.
4. Choose the completion shape before launch. When the project supports a background/detached run with an own-run completion notification, use it: after the start receipt, end the turn and wait for that exact completion. When no such notification exists, disclose it and use the supported foreground completion or existing recovery route. Recover an existing run instead of rerunning it. Do not poll, sleep, tail logs or issue progress loops. A message may not be able to interrupt a foreground wait, so this choice can't be corrected after launch.
5. Keep full logs as runner artifacts; bring only bounded failure diagnostics into context. Classify product, test/fixture or environment failure. Fix what the package owns in the owning worktree, rerun the affected checks, and route the rest as the project's instructions say. Never retry until green or weaken coverage.
6. READY includes exact commit/tree, one line on why the selection covers the change, commands, results, artifact locators, remaining gaps, and any review results and finding dispositions the project requires before READY. Integration owns the final full validation of the combined change; no duplicate whole-suite run beforehand, unless the project's instructions require one.

Capture source_id once per actual execution or resume. Delegation, result collection, reporting and tracker recording cite the original source_id/run result; never recapture merely because custody moved. Capture afresh only for a named source change or a criterion that genuinely requires a new current observation. Read-only review children consume the parent's exact source_id; no raw capture or second identity.

7. Every wait names one session to wake, the exact result, and what delivers it directly to the waiter: the host's own completion (a test-run wait or a delegation wait) or a named session; no polling. Never wait for a conditional resource state: LAUNCH NOW (start at once), or its current holder sends END (its message that the resource is free) directly to the named next waiter. A foreground run the turn itself waits on is not a wait on another session. No watcher; a coordinator assigns any unnamed wait immediately. After every review pair, an implementing parent fixes in-scope, undisputed findings at once. Any open Medium or higher that it does not fix, because it is disputed, out of scope or needs a decision, the review parent sends DIRECTLY to the decision owner, with the candidate, the finding and the requested ruling; that ruling back to the review parent is its waker. The slot END to the scheduler stays a separate message and never counts as reporting a finding. No watcher and no new gate.

No project names or commands are hardcoded here: each repository's own instructions and launcher documentation define them.
